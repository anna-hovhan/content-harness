# House rules for all writing

They apply to every channel and every kind of text: articles, posts, portfolio pages, CVs, cover letters, messages, image text and alt text. Which rule wins is set here, once, for every file of writing rules: first the user's own rules, `{writing_overrides}` for writing and `MY_RULES.md` for confidentiality; then the hard rules, which apply whatever a guide says: sections 1 and 2 of this file, banned phrases included, and the sections a genre's rules mark as hard (sections 1 and 2 of `{social_voice_rules}`); then the user's voice guides, `{social_voice}` for posts and articles and `{tone_of_voice}` for everything; then the remaining defaults, in this file and in the genre rules (`{social_voice_rules}`, `{cv_rules}`, `{cover_letter_rules}`, `{outreach_rules}`). For social posts, the full rule set is `{social_voice_rules}`; this file sums up the rules shared by every channel and adds the ones for long-form and site copy.

Each rule ends with its ID (`HR-...`). This file is the source; any other file that restates a rule, in this repo or in a repo that reads these rules, names the ID next to it, and `python3 scripts/doctor.py` reports a restated rule without its ID, or an ID this file no longer has.

## 1. Truth

- **Never invent** experience, numbers, dates, people, quotes, anecdotes, tool names or motives. Every fact comes from the evidence ledger, the user's files, or the user. `HR-never-invent`
- **Unknown facts** get a visible `[CHECK: what to confirm]`. The user's own story gets `[YOUR MOMENT: what belongs here]`. Never fill either with something plausible. `HR-mark-unknowns`
- **Examples are labelled as examples.** "A note that says 'the pipeline has 13 deals'" reads as an illustration; "the pipeline has 13 deals" reads as a fact. `HR-label-examples`
- **Confidentiality:** follow every note in `MY_PROFILE.md` and `MY_RULES.md`, in the text, the image copy and the alt text. Never name a current employer's customers. `HR-confidentiality`
- **Credit what the work builds on**, by name, with its author. `HR-credit`
- **Fact-check the user's points too.** When the user hands over points to write up (a brain dump, notes, a list of claims), check each claim about tools, the industry or how a system works against the sources and the evidence ledger before writing it. Refine what is partly right, add what the analysis shows, and tell the user which points changed and why. Their opinions stay theirs, written as their view. Set 2026-11-10. `HR-fact-check-user`
- **Say whose work it was.** A personal build is named as a personal build, done outside the user's employment, and work done for an employer is never presented as personal. Set by the user on 2026-11-24, from a correction of 2026-11-22. No script can check it; the self-check in section 6 asks for it. `HR-say-whose-work`
- **Private repos stay private on the site.** Everything on the portfolio site (case studies, blog posts, any site copy) names only the user's public repos, and never names a private repo or describes what one does. It also leaves out repo-internal specifics: the dates of internal events, rule IDs, file and script names, counts of rules, cases or checks, and quotes from the repo's code or docs. The piece describes the approach and its trade-offs; the internals stay in the repo. Set by the user on 2026-11-25. No script can check it; the self-check in section 6 asks for it. `HR-site-private-repos`

## 2. Hard style rules

### 2.1 Core style rules

- **No em dashes or en dashes**, anywhere. Use a comma, a colon, a full stop, or rewrite. `HR-no-dashes`
- **No negative parallelism:** "It's not X, it's Y", "X isn't just A, it's B", "Not because X, but because Y", "Less X, more Y", "X, not just Y", "From X to Y" headlines. Say what the thing is. `HR-no-negative-parallelism`
- **No stock AI phrasing:** the list in `{banned_phrases}` (`system/00-core/banned-phrases.txt` in this repo), which `scripts/test_check_text.py` enforces. The list also has phrases the user retired from their own writing, such as "Let's be honest" (set 2026-11-24); a voice guide or an earlier post that still quotes one does not bring it back. `HR-no-stock-phrasing`
- **No lesson-reveal framing:** "Here's what X taught me about Y", "What building it taught me", "What I learnt", "Lessons I learned". It reads as a template and puts the author on a stage. Give the lesson itself, in the reader's terms: "What I'd pass on to anyone bringing AI into their team", or simply the point. This applies to titles and headings too. `scripts/test_check_text.py` flags it. `HR-no-lesson-reveal`
- **No sentence starts with "Here is", "Here's" or "Here are"**, in titles and headings too: "Here's how it changed...", "Here's what I found", "Here are three lessons". Start with the point itself. `scripts/test_check_text.py` flags it. `HR-no-here-opener`
- **No inflated significance.** Don't make things sound important, profound or life-changing: "Building this changed how I think about...", "What I'd pass on to anyone...", "For the first time...", "The best test of any system...", "rules that matter enormously", "Your colleague will thank you", "I'm genuinely curious". Say what happened and what it does; the reader decides whether it matters. Plain beats grand. `HR-no-inflation`
- **No statements of the obvious.** Cut any sentence a person working in tech already knows: "every new chat starts from zero", "AI can make mistakes", "people use tools they trust", "tools will keep changing", "everything it reads is treated as information". If the reader would answer "yes, obviously", replace it with the specific detail that is new to them, or drop it. `HR-no-obvious`
- **No slogans.** No matched pairs of short fragments that read like a tagline: "Private by default. Shared on purpose.", "Plain words. Real results.", and no number pairs: "1 folder, 3 commands", "Three floors, one rule", "One ask, the week files itself". This applies to titles, headings and image text too. Write the idea as an ordinary sentence: "Everything starts private, and you decide what gets shared." `scripts/test_check_text.py` flags number pairs as errors and short fragment pairs as warnings to read. `HR-no-slogans`
- **No cinematic or dramatic openings.** No montage of sentence fragments ("The strategy deck. The reason we picked vendor B over vendor A. The goal we agreed on in January..."), no staccato run of three or more short sentences ("You read it. You fix what it got wrong. You say yes."), and no storytelling flourish that dramatizes an ordinary problem ("quietly stopped talking about in March", "the head of someone who left last spring"). Open with the problem or the claim, in a full sentence. One short fragment as a second beat after a full sentence is fine ("At least for now."). `scripts/test_check_text.py` flags montages and staccato runs as errors; flourishes need a read. `HR-no-cinematic-openings`
- **No titles or headings that start with "I" or "We".** "I built a shared context layer...", "I gave my company a brain" read as a launch announcement and put the author ahead of the subject. Title the piece with its subject or the claim it backs up: "Shared context for agents is an operating model problem". First person is fine in the text. `scripts/test_check_text.py` flags it. `HR-no-i-we-titles`
- **No reveal formula** ("The result? ..."). A real question the user would ask out loud is fine. `HR-no-reveal-formula`
- **No tricolon on autopilot.** Use the number of items the content actually has. `HR-no-autopilot-tricolon`
- **No sweeping words.** No "nobody", "no one", "everyone" or "everybody" where a specific claim belongs: "Nobody has mapped..." and "nobody wrote down" read as sweeping. Say who did or did not do it, or state the claim the word stood in for: "has to be mapped first", "without a written rule". Set by the user on 2026-11-24, from a correction of 2026-11-22. `scripts/test_check_text.py` flags "nobody" and "no one" as errors, and "everyone" and "everybody" as warnings to read, since a bounded "everyone on the call" can be the specific claim. `HR-no-sweeping-words`

### 2.2 AI writing patterns

Set by the user on 2026-11-11, from Wikipedia's "Signs of AI writing" (WikiProject AI Cleanup, read November 2026, https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing). They are hard rules like those in 2.1 and apply to every channel and kind of text, in the whole piece. Where one differs from the user's own rules (`{writing_overrides}` for writing, `MY_RULES.md` for confidentiality) or a rule in 2.1, that one wins: no dashes at all (so vary punctuation with colons, semicolons and parentheses), `[CHECK: ...]` and `[YOUR MOMENT: ...]` markers in drafts (never in final copy), firm claims only with a source, and jargon where it is the precise word.

`scripts/test_check_text.py` runs the pattern checks (`scripts/ai_patterns.py`). A pattern that is wrong on its own is an error; a pattern that is wrong only in a cluster is a warning that costs points in an AI-pattern score, and a score under 70 fails the check. The AI reviewer covers what patterns cannot see (`system/00-core/test_review-rubric.md`, which also holds the scoring). Not signs either way, so not worth correcting for: perfect grammar, a mix of casual and formal register, formal prose, a few transition words, and citations.

- **Keep the specific fact.** Most of these patterns come from one swap: a specific, unusual fact replaced by a generic claim that sounds important ("built the first train-coupling device" becomes "a titan of industry"). Keep the fact; with none to give, leave the point out and never pad it. Swapping a flagged word for a synonym while keeping the structure breaks the rule too. `HR-ai-keep-specific-fact`
- **No significance, legacy or trend claims.** An ordinary detail does not stand for, shape or add to a bigger story, and the subject is not placed in "an evolving landscape" or "a broader debate". Never argue that something matters ("this matters because", "is a testament", "plays a pivotal role", "underscores its importance", "a key turning point"). `scripts/test_check_text.py` flags the stock forms. `HR-ai-no-significance-claims`
- **Report what coverage said, not that it was covered.** No "featured by leading outlets", "independent coverage", "an active social media presence". Say what the source reported, and never credit your own reading to a source. `HR-ai-no-coverage-padding`
- **State the fact, not the record.** "Jane is a retired civil servant", not "her website identifies her as a retired civil servant". `HR-ai-state-the-fact`
- **No trailing "-ing" commentary.** A sentence does not end on a clause that comments on its own importance: ", highlighting the need for", ", reflecting its focus on", ", fostering", ", ensuring that". Make it a sentence with its own evidence, or cut it. `HR-ai-no-trailing-ing`
- **Name the relationship.** "Taught science at Example University", not "was connected with science education at Example University". `HR-ai-name-the-relationship`
- **Name your sources.** No "experts argue", "observers have noted", "industry reports suggest", "some critics", and no "several sources" for one or two. `HR-ai-name-sources`
- **No challenges-and-future formula.** No "Despite its strengths, X faces several challenges", no vague optimism about plans, no stock "Challenges" or "Future outlook" section. Limits and trade-offs stay in the piece, as specific ones. `HR-ai-no-challenges-formula`
- **Plain headings.** Sentence case, never Title Case. No stock "X and Y" headings ("Awards and recognition", "Challenges and legacy"), no wrap-up headings ("Conclusion", "Final thoughts", "Key takeaways") and no "About me / My interests / Let's connect!" formula. `HR-ai-plain-headings`
- **No cluster of AI vocabulary.** These words travel together: challenge, clearer, dependable, echoed, foster, leverage, matters, multifaceted, practical, prioritize, quietly, steady, universally, underscore, and the fake-scientific causal, empirical, correlate. One is fine where it is the precise word; three in a paragraph is an error. Their synonyms are not suspect. `HR-ai-vocabulary-density`
- **Plain "is" and "has".** Not "serves as", "stands as", "functions as", "represents", "marks", "boasts", "features", "offers", "holds the distinction of being", and not padded forms ("began his career as", "ventured into"). `HR-ai-plain-copulas`
- **No contrast nobody asked for.** The family of rules against negative parallelism extends to "not only... but also", "it's not just...", "no X, no Y, just Z", "rather than simply...", and a contrast spread over two sentences ("X was known for A. Its real value, however, lay in..."). "Rather than" is fine for a real alternative the reader would weigh. `HR-ai-no-unasked-contrast`
- **No definition of a topic as a proper noun.** Do not open by defining a generic topic or list title ("The skills list is a collection of..."). Say what the thing does. `HR-ai-no-topic-definition`
- **Plain verbs.** Wrote, moved, used, tried, died; not authored, relocated, utilized, endeavoured, passed away. `HR-ai-plain-verbs`
- **No "holds" for "works" or "applies".** A rule, a check or a claim does not "hold": no "a rule holds when...", "whether it holds", "it holds up in production", "holds true", "the rules hold for every channel". Use the plain verb for what happens: the agent follows the rule, the check runs, the claim is true, the rule applies to every channel. A file that holds text is the ordinary verb and is fine. The same goes for "lives" and "sits" when a thing is simply in a place ("the rules live in one file", "the check sits in CI"): write "are in", "runs in". Set by the user on 2026-11-24. `scripts/test_check_text.py` flags the forms where the verb clearly has no object as errors ("holds when", "holds until", "holds true", "holds up", "whether it holds", "the rule holds."), and warns about "holds for", "holds in", "lives" and "sits"; any other form needs a read. `HR-ai-no-holds`
- **No list that repeats its opening word.** A list whose items all open with the same word reads as a cadence: "my writing, my notes, my images, and my portfolio site", "your team, your tools, your data". Name the things themselves, and say the shared word once or leave it out: "a content harness, a design assistant, a notes app and my site". Two items are fine ("my name and my email"). Set by the user on 2026-11-24. `scripts/test_check_text.py` flags three or more short items in a row (one or two words each) that open with the same possessive; longer items and other repeated openers need a read. `HR-ai-no-repeated-list-opener`
- **Vary the rhythm.** Mix long and short sentences and use colons, semicolons and parentheses, since text tuned off the dash falls back on periods and commas and sentences of 8 to 20 words, and that flatness is a sign too. A run of short sentences is still a staccato run. `HR-ai-varied-rhythm`
- **No brochure tone.** No nestled, in the heart of, vibrant, groundbreaking, renowned, a diverse array, a rich tapestry, natural beauty; and showcasing, exemplifies or "commitment to" in a cluster. `HR-ai-no-brochure-tone`
- **No summary wrap-ups.** No "In summary", "In conclusion", "Overall,", "To sum up", and no paragraph that ends by restating its own point. The close is a reference and a question. `HR-ai-no-wrap-up`
- **No abrupt endings.** The last paragraph ends where the piece means to, with closing punctuation. `HR-ai-no-abrupt-end`
- **Prose by default.** An article, a post or a cover letter argues in paragraphs. "**Label**: explanation" bullets, three in a row or more, are for reference material. `HR-ai-prose-default`
- **One H1, levels in order.** The title is the only H1, and headings go down one level at a time. `HR-ai-heading-levels`
- **No emoji markers.** No emoji at the start of a heading or list item, unless the user's own writing rules (`{writing_overrides}`) or the user's own posts do exactly that. `HR-ai-no-emoji-markers`
- **Straight quotes.** Use " and ', not curly quotes, unless the channel or the user's own posts use them. `HR-ai-straight-quotes`
- **No chatbot talk in the copy.** Nothing addressed to the user: "I hope this helps", "Certainly!", "Would you like...", "Let me know if", "a more detailed breakdown", "check this before publishing", "As an AI...", and no planning notes to the writer ("LEAD: expand to two paragraphs"), hidden comments included. Notes for the user go in the summary that comes with the piece, never in the piece. `HR-ai-no-chat-residue`
- **Gaps go to the user, not into the text.** The text never says what is missing or guesses what it "likely" is: no "while specific details are limited", "not widely documented", "based on available information", "maintains a low profile". A gap becomes `[CHECK: ...]` or `[YOUR MOMENT: ...]` in the draft and an item in the summary. `HR-ai-no-gap-hedging`
- **No corrective framing or teacher-style hedges.** No "It is important to note", "It's worth noting", "should be treated as speculative rather than definitive", "does not by itself establish", and only rarely "should not be confused with". Say what the evidence shows, at the strength it shows it. `HR-ai-no-corrective-framing`
- **No template blanks.** No "[Company Name]", "(add your URL here)", "(if available)", "2026-XX-XX", "example.com/source1", "Example Source Title". Final copy carries no marker of any kind. `HR-ai-no-template-blanks`
- **Format for where it lands.** A LinkedIn post renders no markdown: no `**bold**`, `#` headings, `---` dividers or `[text](url)` links, only plain text and bare URLs. Portfolio copy carries the formatting its CMS field takes. No copy arrives wrapped in a code block. `HR-ai-channel-markup`
- **No interface artefacts or tracking parameters.** No `contentReference[oaicite:...]`, no `↩`, and no `utm_source=chatgpt.com`, `utm_source=openai`, `utm_source=copilot.com` or `referrer=grok.com` in a link. `HR-ai-no-artefacts`
- **Change notes say what changed.** A summary to the user, a commit message or a feedback-log row names the change ("Cut the second paragraph's analogy"), not "refined for clarity and flow". No stacked compliance claims (ensured, adheres to, enhanced, streamlined), no list of what was left unchanged, no "addressed feedback", no "Comprehensive rewrite:" opener, no "added verified information". The commit hook flags these. `HR-ai-specific-change-notes`
- **No customer-service register.** No "I have carefully reviewed...", no apology for inconvenience, no headed sections in a short reply, no rule that does not exist. `HR-ai-no-service-register`

## 3. A tech-savvy reader, and knowledge shared as a practitioner

Set by the user on 2026-11-10, for every channel: articles and posts above all. The default reader works in or close to tech: they use AI tools at work, know the common terms, and read to learn how someone else built or solved something. Write for them as a peer. When a piece has another reader (a recruiter's first screen, a client outside tech), the brief says so and sets the level of detail.

### Use the field's own terms

- **Jargon is welcome where it is the precise word.** LLM, agent, context window, RAG, embeddings, evals, MCP, tool calls, prompt injection, fine-tuning, API, repo, pull request, markdown, CI: use them without a definition. `HR-precise-jargon`
- **No explaining down.** No "in plain words", "in simple terms", "simply put", "think of it as", "picture this", "imagine a...", and no reassurance that the reader needs no technical skill ("no engineering needed"). No analogy that stands in for a term the reader already knows: an agent stays an agent, never "a very diligent chief of staff"; access layers stay layers, never "three floors of a building". `scripts/test_check_text.py` flags the stock phrases; analogies need a read. `HR-no-explaining-down`
- **Gloss only what is niche**, once, in technical words: the project's own names, a little-known tool, a term the user coined. "Obsidian, a local-first markdown editor." `HR-gloss-niche-only`
- **A metaphor earns its place** only when it shows something the term does not, such as a property or a failure mode. Then it is used the same way everywhere. `HR-metaphor-earns-place`
- **One term per concept**, chosen once in the brief's terms table and used in the text, the visuals and the alt text alike. `HR-one-term`
- **Concrete beats abstract:** the prompt, the config, the failure mode, the step that broke, the Friday afternoon. `HR-concrete`
- **Short paragraphs**, one idea each. Bold at most one phrase per paragraph. `HR-short-paragraphs`
- **Say each idea once.** Each idea goes in the one section where it belongs. The thesis may return once, as the takeaway; a mechanism, a layer or a limit is not restated in the hook, the body and the close. When the user's own text says an idea twice, keep it once, in its best place. Set 2026-11-13. `scripts/test_check_repetition.py` warns about paragraph pairs that make the same point and about phrases that recur across many paragraphs. `HR-no-repeated-idea`
- **Keep the detail the argument needs.** Counts, command, skill and hook names, and step-by-step ordinary behaviour (a dry run shows a diff before it writes, a feed lists its connectors) belong to the repo's README. The piece keeps the decision, its reason and its trade-off, and each paragraph tells a practitioner something they could not guess. Set 2026-11-13. `HR-detail-budget`

### Share knowledge as a practitioner

Every piece reads as a practitioner telling peers what they built or tried, how it works, which decisions they made and why, and where it stops. It never reads as a product page, an ad, a launch announcement or a pitch.

- **Describe, and let the reader judge.** Say what the thing does and how. No promised outcomes ("nobody spends Monday morning chasing status", "saves hours every week") unless they were measured and the ledger has the measurement. No sales adjectives: powerful, effortless, cutting-edge, best-in-class, revolutionary, game-changing. `HR-describe-not-sell`
- **Show the how and the trade-offs:** the design decisions and their reasons, the alternatives considered, the costs, what broke, what the user would change, the honest limits. A piece with only upsides reads as an ad. These come from the ledger or the user like any other fact; a missing one gets `[CHECK: ...]` or `[YOUR MOMENT: ...]`, never a plausible guess. `HR-show-trade-offs`
- **Be fair to the alternatives.** Say what they do well before saying why the user chose differently. `HR-fair-alternatives`
- **Specific, checkable claims:** a number with its source and date, a behaviour the user observed. Unmeasured benefits stay out. `HR-checkable-claims`
- **The close is a reference and a question.** A link to the work, a real question to peers about their own experience, a practical caveat, or an offer to talk about the topic. No call to adopt, try, sign up or buy, no urgency, no "DM me for access". Asking for feedback on open work is fine. `HR-close-reference-question`
- **No launch register:** "excited to share", "proud to announce", "introducing...", exclamation marks for emphasis. `scripts/test_check_text.py` flags the stock phrases. `HR-no-launch-register`
- **The strength shows through the work:** the reasoning, the decisions, the candour about limits. The piece never claims qualities for the user. `HR-strength-through-work`
- **CVs and cover letters** make a case by design. There this rule means the case rests on specific facts, in sober words, with no sales vocabulary. Their wording rules, `{cv_rules}` and `{cover_letter_rules}`, win over this section where the two differ; their steps and formatting belong to the workflow that writes them.

## 4. The author's voice

- **Posts and articles** sound like the user's own published posts, as `{social_voice}` describes them, never like their CV. No CV verbs (spearheaded, drove, leveraged, orchestrated, championed, delivered, owned, enabled, empowered), at most one number per post, no credentials in passing. `HR-voice-posts`
- **The voice guide comes first.** Text for a post or an article, down to one line for one, is drafted from `{social_voice}`, the one description of how the user writes; in this repo a hook loads it at every session start (`docs/voice.md`), and a session without it reads the file before the first draft. The user's published posts in `{social_samples}` are what the guide is built from: they are read to refresh the guide, not for each piece. Match the guide's lines the user picked and turned down, since a balanced, carefully worded sentence ("holds up in production only as well as the process it automates") can score 100 on `test_check_text.py` and still not sound like the user. A line the user picks or turns down goes into that section of the guide, and a picked one also becomes a `pass` case. Set 2026-11-24. `HR-voice-guide-first`
- **CVs and cover letters** follow their wording rules, `{cv_rules}` and `{cover_letter_rules}`, in the user's general voice (`{tone_of_voice}` and the samples in `{voice_samples}`); their steps and formatting belong to the workflow that writes them.
- **Portfolio pages** come between the two: first person, direct, specific, in the field's terms, with the evidence a hiring manager looks for (problem, decisions, proof, honest limits).

## 5. Career-coach lens

Every piece also answers: what does this show about the user, and to whom?

- Name the strength the piece demonstrates (in the brief, not necessarily in the text).
- Prefer the lesson a reader can use over a list of what the user did.
- Keep a link between channels: a post can point to the article, the article to the portfolio page, the cover letter to the case study. Each link must be public and live.

## 6. Self-check before showing a draft

- [ ] One takeaway, and the reader could repeat it
- [ ] Every fact in the evidence ledger, or marked `[CHECK]`
- [ ] Every personal moment is the user's, or marked `[YOUR MOMENT]`
- [ ] `scripts/test_check_text.py` passes: no dashes, no banned phrases, no montage or staccato run, no title starting with "I" or "We", word limit kept, no error from the AI-pattern checks (section 2.2) and a score of 85 or more; every warning it prints is read and fixed or deliberately kept
- [ ] Read once for what patterns cannot see (section 2.2): a generic claim where a fact belongs, a contrast nobody asked for, a topic defined as a proper noun, chatbot talk or a hedge about missing information
- [ ] The title and the first paragraph read once more on their own, against the voice guide, since they set the register: the title states the subject or the claim, and the opening states the problem in full sentences, with no flourish
- [ ] Read it once more for tone: nothing made to sound bigger than it is, no sentence a tech reader already knows
- [ ] A post or an article, or one line for one: drafted from the voice guide and read against its lines the user picked and turned down, since a script score of 100 does not show the voice
- [ ] Written for a tech-savvy peer: the field's terms used without definitions, nothing explained down, no analogy standing in for a term the reader knows
- [ ] Reads as knowledge sharing: how it works, the decisions, trade-offs and limits are there; no pitch, no promised outcome, no sales adjective; the close shares a link or asks a question
- [ ] Each idea appears once (idea map, workflow step 3b); `scripts/test_check_repetition.py` warnings read; nothing included only because it is in the ledger
- [ ] Terms table followed in text, visuals and alt text: one term per concept
- [ ] Every `[IMAGE vN]` marker has a row in `visuals.md`, and every row a marker
- [ ] Every visual rendered and looked at at final size
- [ ] Confidentiality respected in text, image copy and alt text
- [ ] Whose work it was is plain: a personal build named as one, and an employer's work never presented as personal
- [ ] Site copy (a case study, a blog post): no private repo named or described, and no repo-internal specifics (dates of internal events, rule IDs, file names, counts, quotes from the repo)
- [ ] Every link public and live
